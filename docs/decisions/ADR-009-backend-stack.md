# ADR-009 — 后端采用 Nakama + PostgreSQL/Redis + Agones/K8s

- 状态：accepted
- 日期：2026-10-17
- 决策者：Tech Lead + Human
- 关联 REQ：REQ-TECH-003/004/005
- 影响范围：账号、社交、匹配、经济、部署、成本

## 1. 背景

需要账号/好友/公会/聊天/排行/匹配、经济账本、战斗服编排；团队小，不想从零写所有 meta 服务。

## 2. 选项

| 方案 | 优点 | 缺点 | 风险 |
|---|---|---|---|
| Nakama + PG/Redis + Agones | 开源、社交/匹配/排行成熟；Go 可扩展；可自托管 | 经济/拍卖需自定义；运维成本 | 中 |
| PlayFab | 托管、功能全 | 成本/锁定；实时弱 | 中 |
| 全自研 | 完全控制 | 慢、风险高 | 高 |
| Nakama + Hiro | 经济/库存/战令加速 | Hiro 许可/锁定 | 中 |

## 3. 决策

选择 **Nakama + PostgreSQL + Redis + Agones/K8s**。

- Nakama：账号、好友、公会、聊天、排行、基础匹配。
- 自定义经济/拍卖服务（Go 或 C#）：双录账本、幂等、审计。
- PostgreSQL 16：账号/角色/背包/账本/订单；Redis 7：会话/在线/队列/限流。
- Kafka/NATS：战斗结果/事件/分析；Agones：Fusion headless 战斗服编排。
- Hiro 作为可选加速；若使用，评估许可/锁定。

## 4. 后果

### 正面
- 快速搭 meta；社区/文档成熟；可自托管控成本。
- 经济/拍卖可定制，避免被平台限制。
- 与 K8s/Agones/观测栈集成好。

### 负面/代价
- 需要后端/运维人力；Nakama 自定义逻辑需 Go/TypeScript/Lua。
- 经济/拍卖自研有安全/一致性风险；必须双录账本/审计。
- 多区/容灾需要额外设计。

### 跟进
- TDD 定义数据模型/API/账本/幂等/审计。
- 成本模型按 1k/10k/50k CCU。
- 评估 Hiro 许可与替代。

## 5. 复访触发

- Nakama 扩展/功能不满足。
- 自研经济成本过高/事故。
- PlayFab/Hiro 方案更优。
- 多区/合规要求变化。
