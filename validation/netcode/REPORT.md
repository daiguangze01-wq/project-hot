## 0. 结论先行

### 0.1 三个决策问题的答案

| # | 问题 | 模型结论 | 置信边界 |
|---|---|---|---|
| Q1 | 100ms 完美格挡在 **30Hz tick + 200ms 回放 + 2–3 帧输入缓冲** 下是否公平？ | **在线不可直接上线，本地/离线 100ms 保留。** 成功率本身达标（RTT 80/100ms：99.7%/99.4%），但若把在线窗口压到 100ms 并沿用文档的“1 tick 容差”，**误判率 5.7% > 5%**（30Hz；60Hz 为 5.4%/5.1%），不满足 M0 公平验收。若把服务器容差从“1 tick”降到 0.5 tick（30Hz ≈16.7ms），误判可降到 4.4–4.9%（30Hz）/3.7–4.0%（60Hz），成功率仍 ≥98.0%/≥97.6%，**但只剩 ≤0.6pp 的误判余量，且 C+X chord 延迟/时钟误差会迅速吃掉余量**（模型：chord 延迟 0–40ms 时 100ms 窗口误判升到 16.9–22.2%）。 | 模型；误判对“测试人群的时序分布”和容差定义敏感（§2.4/§7.3） |
| Q2 | **150ms 在线窗口 + 1 tick 容差** 够不够？ | **对 RTT 80/100ms 够，对 150ms 有条件，对 200ms 不够。** 30Hz、在线窗口 150ms、cap 200ms、defender-favoring ON、2 帧缓冲下：RTT 80/100ms 成功率 100.0%/99.7%、误判 0.5%/0.2%（专家型 σ=25ms）；RTT 150ms 成功率 81.7%（要求 cap=200；cap=150 只有 18.4%）；RTT 200ms 18.4%。**真正的约束不是“150ms 窗口 + 1 tick”，而是防御交互回放 cap 与容差大小**：cap 150→200 把 RTT 100ms 的 82.4% 提到 99.7%，把 RTT 150ms 的 18.4% 提到 81.7%。 | 模型；RTT 150ms 的 81.7% 对“1 tick 容差=33ms”的宽口径敏感，60Hz（1 tick=16.7ms）为 74.1% |
| Q3 | 是否必须 **60Hz 排位**？ | **不是 M0 成功率验收的硬前提**（30Hz + 150ms + cap200 已通过 ≥70%/≤5%）。但 60Hz 有实质公平/精度收益：纯网络/量化 p95 误差 25.8ms→12.9ms（σ=0），同等 1 tick 容差下误判 5.7%→5.4%（100ms 窗口）/0.5%→0.4%（150ms 窗口）；休闲玩家（σ=50ms）150ms 窗口误判 8.5%→6.8%（1 tick）或 7.1%→4.6%（0.5 tick）。**建议：30Hz 为 M0/PvE 基线，排位 1v1/3v3 把 60Hz 从“可选”升级为“推荐/默认回退”**，并把排位最大 RTT 锁在 ≤100ms（目标）/≤150ms（容忍）。 | 模型；60Hz 服务器成本未评估（非本任务） |

## 1. 这不是 Fusion/Unity 实测（边界声明）

- 本报告是**离散事件 Monte Carlo 模型**：只模拟“攻击时间线 + 输入时间戳 + 服务器判定策略 + 网络/量化误差 + 人因时序误差”，**不包含**位置/命中盒重叠、动画、Fusion 预测回滚、渲染、输入延迟、服务器实现细节、玩家学习/预测行为。
- 因此：
  - 模型能回答“**若**实现为输入时间戳 + cap 内追溯 + defender-favoring，**理论上**成功率/误判的上下限”，用来指路 M0；
  - 模型**不能**证明 Fusion 2 实际能达成这些数字。M0 必须用引擎实测复核（§6 给出最小矩阵）；实测不达标时按 §6.5 的降级阶梯处理。
- 本报告的“成功/误判”是模型定义（§2.4），与 docs/02 §4.3 的“成功率 ≥70%、误判 ≤5%”口径需要 M0 对齐（尤其“误判”的测试人群与输入分布，见 §7.3）。

## 2. 方法与假设

### 2.1 时间线（与 `run.py` `simulate()` 一一对应）

单位 ms，同一服务器时钟；相对时间，攻击命中为锚点。

```text
轻击: startup 8f + active 3f @60fps → 命中偏移 HIT = (8 + 3/2) × 16.667 = 158.333ms
服务器命中检测:   t_detect = t_hit + delta,        delta ~ U(0, 1 tick)       # 30/60Hz => 0–33.3 / 0–16.7ms
人类时序误差:     e_h ~ N(0, sigma),               sigma ∈ {0, 25, 50}ms      # 0 = perfect-timing 对照
客户端采样:       q_c ~ U(0, 16.667ms)             # 60Hz 输入采样
视角抖动:         j_view = U(-J, J) 当 interp=0；interp=33 时 = 0（被插值缓冲吸收），J ∈ {0,10}ms
按压时刻:         t_press = t_hit + OW + interp + j_view + e_h + q_c
                  OW = RTT/2（对称网络）; interp ∈ {0, 33}ms
上行抖动/缓冲:    j_up ~ U(-J, J); late_j = max(0, j_up - B×16.667ms)
服务器收到:       t_arr = t_press + OW + late_j
丢包:             B+1 份冗余；全丢概率 = loss^(B+1)
服务器判定:
  defender-favoring ON : t_guard_ev = t_press - (OW + interp)          # 客户端时间戳 + 视图延迟补偿
                         允许 t_arr ≤ t_detect + cap 内追溯            # defense interaction cap
                         窗口 = W/2 + 1 tick (grace)
  defender-favoring OFF: t_guard_ev = t_press；要求 t_arr ≤ t_detect；窗口 = W/2（严格实时）
判定:    完美格挡 = 未丢包 ∧ 满足到达/追溯条件 ∧ |t_guard_ev − t_detect| ≤ 窗口
```

“防御者按看到的命中时刻出手”= `t_hit + OW + interp`，即**先感知再按**；模型因此把“看到起手再反应”的可行性单独作为诊断（§3.11），而不影响主判定。

### 2.2 矩阵规模

| 维度 | 取值 | 说明 |
|---|---|---|
| tick | 30 / 60 Hz | 服务器命中检测粒度（按 TASK-061 SPEC；docs/03 §5.1 的 60Hz 子步另作敏感性 T16c） |
| 输入缓冲 | 0 / 1 / 2 / 3 帧 | 服务器侧对称缓冲：吸收抖动 + B+1 份冗余 |
| RTT | 0 / 50 / 80 / 100 / 150 / 200 ms | 对称，单向 = RTT/2 |
| 抖动 | 0 / 10 ms | 上行；interp=0 时另加视角抖动 |
| 丢包 | 0 / 2 % | 每包独立；冗余 B+1 份 |
| 完美格挡窗口 | 100 / 150 ms | 以真实命中为中心 |
| 回放 cap | 150 / 200 ms | 防御交互追溯窗口上限 |
| defender-favoring | on / off | 见 §2.1 |
| 插值延迟 | 0 / 33 ms | 额外建模维度 |
| 人因 σ | 0 / 25 / 50 ms | 0 = perfect-timing 对照；25 = 训练有素；50 = 休闲/高噪声 |
| 合计 | **9,216 配置 × 10,000 trials = 92.16M trials** | 结果：`results.csv`（35 列） |

另：`sensitivity.csv`（78 行）覆盖半 tick 容差、0 容差、chord 延迟、预压补偿、200ms 窗口、到达时间判定、60Hz 子步命中、σ=50 等敏感性场景；`sanity_checks.csv` 10 项模型自检全部 PASS（§3.12）。

### 2.3 假设清单（模型边界）

| # | 假设 | 影响/若违反 |
|---|---|---|
| A1 | 轻击 8f startup / 3f active / 命中在 startup+active/2（docs/00 §3.5） | 换招式需重算命中偏移 |
| A2 | 60fps 帧数据、60Hz 客户端输入采样 | — |
| A3 | 双方 RTT 对称（one-way = RTT/2） | 非对称（如下行更差）会引入系统偏差；M0 必须测 |
| A4 | 防御者是“理想预判者”：按压中心 = 感知到的真实命中 + N(0,σ) | 真实玩家还要“读招/预测”，模型不测预测能力（§3.11） |
| A5 | 服务器/客户端时钟与 tick 映射无误差（ClientTimeMs 精确映射） | 真实 Fusion 有估计误差；**这是本模型最乐观的假设之一**；M0 必测（§6 C4） |
| A6 | 服务器输入缓冲对双方对称：只增加绝对延迟、不改变相对时序；作用为抖动吸收与冗余 | 若 Fusion 输入缓冲实现为不对称/客户端输入延迟，需把 B×16.7ms 加到 defender 侧；M0 必测 |
| A7 | 冗余 = B+1 份、抖动吸收 = B 帧 | Fusion 实际为固定 3 帧冗余；M0 按实际配置复核 |
| A8 | 主矩阵按“服务器 tick 边界判定命中”（TASK-061 SPEC）；docs/03 §5.1 的 60Hz 战斗子步作为敏感性 T16c | 60Hz 子步只把 σ=0 的量化误差减半（T16c），对含容差的误判改善很小 |
| A9 | interp=33ms 吸收 ±10ms 视角抖动；interp=0 暴露全部抖动 | 真实插值实现需 M0 确认 |
| A10 | 主矩阵 defender-favoring = 客户端时间戳 + 视图延迟补偿 + cap 内追溯 + **1 tick 容差**；推荐值见 §0.2（0.5 tick，敏感性 §3.7） | 若实现缺少任一项，结果分别退化（T7/T12） |
| A11 | “误判”= 服务器判完美、但真实输入时序不在窗口内；窗口以真实命中为中心 | docs/00 §11 写“受击前 100ms 内”，口径可能是单边窗口 → **待核实**；见 §7.3 |
| A12 | 伤害经济示意：完美 0、普通格挡 20%（6）、未挡 30（docs/02 §4.5） | 仅用于 mean_damage 相对比较，不是平衡结论 |
| A13 | 主矩阵不含位置/防御锥/连段/多段命中/闪避 | 位置类延迟补偿（命中盒 rewind）需 M0 另测 |
| A14 | 主矩阵不含 C+X chord 识别延迟、手速/键盘 rollover、宏 | chord 作为敏感性（0–40ms）；rollover 见 TASK-062 |
| A15 | 不含反作弊/宏检测、服务器成本、AOI | 非本任务 |
| A16 | 完美格挡前瞻窗口每 trial 独立；无跨攻击记忆/学习 | 真实玩家的预测能力是另一条曲线 |

**模型对真实 FUSION 的映射提示**：模型中“防御交互 cap 内的追溯”对应 docs/02 §4.3 / docs/03 §5.4 的“防御交互单独 cap / defender-favoring”；“客户端时间戳 + 视图延迟补偿”对应 docs/03 §5.4 的“用输入时间戳，不只看按键 tick”。docs 写防御交互 cap = 150ms、命中盒回放 ≤200ms；模型把 cap 作为**追溯判定的时间上限**来评估，若引擎实现口径不同，M0 必须按实现重新标定（§6/§7.3）。

### 2.4 指标定义（避免歧义）

| 指标 | 定义（模型内） | 用途 |
|---|---|---|
| `perfect_guard_success_rate` | 服务器判完美的 trial 比例（所有 trial） | 玩家体感成功率；受 σ 与网络共同影响 |
| `true_in_window_rate` | `|j_view + e_h + q_c| ≤ W/2` 的比例（“真实时序在窗口内”） | 纯人因/执行质量（不含网络交付） |
| `success_given_in_window` | 在真实时序在窗内的 trial 中，服务器判完美的比例 | **纯网络/实现交付率**（分离网络误差） |
| `false_positive_rate` | 服务器判完美 ∧ 真实时序**不在**窗口内的 trial 比例 | 攻击方公平性 / “误判”（docs/02 M0 验收） |
| `false_positive_given_out_window` | 在真实时序不在窗内的 trial 中，服务器误判为完美的比例 | 条件误判率 |
| `p95_timing_error_ms` | p95(`|t_guard_ev − t_detect|`)：服务器观测到的绝对时序误差，含人因+采样+量化 | 服务器判定精度 |
| `p95_human_error_ms` | p95(`|e_h|`) | 人因分量 |
| `p95_network_error_ms` | p95(`|(t_guard_ev − t_detect) − e_h|`)：网络视角抖动+采样+服务器 tick 量化 | 网络/实现分量 |
| `retro_applied_rate` | 判完美且 `t_arr > t_detect` 的比例（命中已被判定后被追溯撤销） | 攻击方观感公平（“被回放格挡”） |
| `mean_damage` | 完美 0 / 普通格挡 6 / 未挡 30（示意） | 相对代价 |
| `visible_telegraph_to_hit_ms` | `158.3 − (RTT/2 + interp)`：从感知到起手→真实命中的可见预警时间 | 判断“看到再格挡”是否可能 |

> 注：当某条件在当前配置下没有样本时（例如 σ=0 时没有“真实时序在窗口外”的 trial），对应条件率在 CSV 中记为 `nan`；成功率/误判等无条件指标不受影响。

| 150 | 50 | 67.9% | 86.2% | **75.8%** | 2.6% | 96.8 | 25.9 |

**读法**：RTT ≤100ms 时，给定玩家时序在窗内，服务器交付率 ≈100%——失败主要来自人因（σ）与容差造成的误判；RTT 150ms 时“窗口内交付率”掉到 82%，**网络/回放 cap 成为主因**。σ=0 时服务器观测 p95 = 25.8ms（30Hz）/ 12.9ms（60Hz），纯 tick 量化+采样；σ=25 时 p95 总量 ~55ms，其中人因 ~49ms。

## 4. 讨论：约束排序与设计含义

1. **约束排序（对在线完美格挡）**：① 判定方式（必须时间戳+追溯）→ ② 防御交互 cap（RTT≥120ms 时）→ ③ 误判/容差（100ms 窗口时）→ ④ tick（精度/公平）→ ⑤ 输入缓冲（丢包/抖动）。
2. **“窗口”不是越大越好**：窗口从 100→150ms 会把成功率推满，但误判取决于容差与人群；扩大到 200ms 不能解决 cap 不足（§3.4）。窗口应与“本地 100 / 在线 150”分轨（docs 已有该意图）。
3. **1 tick 容差与 tick 率绑死是隐患**：30Hz 下 1 tick=33ms = 100ms 窗口的 1/3。建议容差按**半 tick** 定义（30Hz ≤16.7ms；60Hz ≤8.3ms），不要让 30Hz 的容差比 60Hz 大一倍。
4. **60Hz 的收益是“公平/精度”，不是“成功率”**：在 cap=200 的交付下，30Hz/60Hz 成功率接近；60Hz 主要降低误判与量化误差，并让 100ms 在线窗口成为可能。是否值得服务器成本，需要 M0 实测 + 成本评估（非本任务）。
5. **对攻击方的公平性需要产品层设计**：追溯撤销率接近 100%（RTT≥80ms）。建议 M0 同时测“被回放格挡率/命中撤销率”，并在 UI/打击反馈层设计解释（如格挡预兆、命中确认延迟、战斗日志），否则会被玩家感知为“打中了却被吞”。这也是 REV-002 B2 指出的“回放方向”问题。
6. **反作弊/宏**：在线完美格挡是“精确时序”机制，输入间隔异常规律/脚本宏检测应把“完美格挡时序分布”纳入监控（docs/03 §11 已有方向）。

### 6.5 不达标降级阶梯（按顺序）

1. 先确认实现正确性：时间戳判定、cap 追溯、defender-favoring、60Hz 子步命中、冗余输入（C1/C2 负对照先过）。
2. 再调容差：1 tick → 0.5 tick（30Hz ≤16.7ms；60Hz ≤8.3ms）。
3. 再评估 cap：150→200ms（需 ADR/Human，见 §5.3）。
4. 再评估 60Hz：排位默认 60Hz（成本评估）。
5. 最后动窗口：在线 150→100ms 只在 60Hz + 容差 0.5 tick + chord/时钟达标时考虑；本地 100ms 不动。
6. 都不达标：按 docs/02 §4.3 触发「30Hz/200ms 基线重开」决策（REV-002/ADR-008 §5 口径）。

## 7. 限制与待核实

### 7.1 模型局限（结论不可外推的部分）

1. **无位置/命中盒**：只测时序；命中盒 rewind（RTT/2+interp，cap 150/200）对“命中是否发生”的影响未建模（docs/03 §5.4/§6.3 的 capsule/cylinder overlap 需 M0 测）。模型里 `hitbox_rewind_ms = min(RTT/2+interp, cap)` 在 RTT≤200/interp≤33 内从未触顶（max 133ms），**说明位置 rewind 的 cap 150/200 在本参数域不构成约束；防御时序的 cap 才是**（§3.4）。
2. **无预测/读招能力**：防御者按“感知命中 + N(0,σ)”出手（A4），不模拟“读起手→预判命中”的学习曲线；真实在线完美格挡是预判机制（§3.11），人因 σ 可能随经验/招式变化。
3. **时钟/tick 映射零误差（A5）**：这是最乐观假设；真实 Fusion 的输入时间戳映射误差会直接吃容差。
4. **输入缓冲语义（A6）**：模型假设服务器侧对称缓冲；Fusion 实际实现（input buffer/input delay）若不对称，需把延迟加到 defender 侧重算（M0 A5/C4）。
5. **无 C+X chord 延迟（主矩阵）**：敏感性显示 0–40ms chord 会显著改变 100ms 窗口结论（§3.10）；真实 chord 延迟需实测（C5）。
6. **无多段/连段/招式差异**：只测轻击；重击（18f startup）会让可见预警更长（更利于反应/预判），但命中偏移也变化。
7. **无服务器实现/网络拓扑/成本**：30 vs 60Hz 的服务器 CPU/带宽成本未评估，不能仅凭本报告决定 60Hz 排位。
8. **无作弊/宏**：精确时序机制易被宏利用，反作弊策略另行评估（docs/03 §11）。

### 7.3 “误判率”对测试人群敏感

模型显示：同一配置（30Hz/150ms/1 tick 容差）σ=25 误判 0.5%，σ=50 为 8.5%（RTT80）——因为“真实时序不在窗内”的概率随人群噪声上升，而服务器容差仍会放行其边界样本。**M0 的“误判 ≤5%”必须定义人群/输入分布**（例如：训练型 bot σ≈25 + 真人 cohort 分开统计；或对每类玩家分别给出阈值）。否则同一实现可以“通过”也可以“不通过”。

### 7.4 攻击方观感（追溯格挡）未量化

模型 `retro_applied_rate` 在 RTT≥80ms 接近 100%，输入到达晚于真实命中 121–141ms（§3.11）。这意味着攻击方在本地已看到命中，随后被服务器撤销。是否可接受是**产品/UX 决策**（反馈设计、命中确认时机、格挡预兆、战斗日志），模型只能提示风险，不能判定“公平”。

### 7.5 与现有评审的对应

- REV-002 B2 的担忧（“服务器只回放受击盒、不回放防御输入 → 判晚；连防御状态一起回放 → 攻击方被吞”）在模型中被量化为：无 defender-favoring 时 RTT≥80ms 成功率 0–0.5%；有 defender-favoring 时成功率恢复但追溯撤销接近 100%。**结论：必须回放防御输入，但要把“攻击方被吞”作为 M0 观感/公平验收项，并用 cap/容差控制撤销窗口。**
- REV-002 建议“把 200ms 回放上限降到 ≤100ms 或对防御交互单独 cap、给防御者 50–100ms guard grace、排位默认 60Hz”：
  - “防御交互单独 cap”：模型支持，但方向相反——**150ms 不够，应 200ms**（若排位支持 RTT≤150ms）；
  - “guard grace 50–100ms”：模型显示 1 tick（33ms@30Hz）已使 100ms 窗口误判超 5%，50–100ms grace 会显著放大攻击方不公平；**建议 grace 用 0.5 tick（30Hz ≤16.7ms；60Hz ≤8.3ms）**；
  - “排位默认 60Hz”：模型支持作为公平/精度手段（§3.6/§3.7），但不是成功率必要条件。
