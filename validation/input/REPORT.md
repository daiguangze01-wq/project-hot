## 0. 结论（TL;DR）

1. **NKRO / 6KRO：TASK-062 要求的全部组合都可同时按住，无计数风险。**
   主矩阵最大 4 键（正交）/ 5 键（斜向），都在 6KRO 的 6 键上限内（NKRO 不限）。
   仅极限上下文「V + 斜向 + Z+X+C = 6 键」正好用满 6KRO，无余量（见 `context_matrix.csv` X07）。

2. **2KRO：只有 1–2 键组合可同时按住（15 个组合中的 10 个）；3 键及以上组合必须顺序输入、改键或 Space 替代。**
   2KRO 不可同按：`Z+X+C`、`方向+Z+C`、`方向+Z+X`、`方向+Z+X+C`、`方向+X+C`。
   另外 `方向+C` 正交方向 2 键可同按，但**斜向方向**（8 向移动 = 2 个方向键）= 3 键，2KRO 不可。

3. **顺序输入回退（软件层）只在文档承诺的路径上验证成立，且对引擎有额外要求。**
   - 必杀顺序 `Z→X→C`（≤250ms）的「干净」条件**不是「X 松开后 3f 内按 C」**，而是「C 按下距 X **按下** ≤3f（50ms，输入缓冲）」且不触发防御抢判：X 仍按住时若 C−X ≤40ms → 判防御，40<C−X≤50ms 窄带仍可干净必杀，C−X >50ms → 中间普攻/特殊技先提交（即使 C 距 X 松开只有 3f，如 X↓50/X↑60/C↓110）。精确条件、探测表与 X 按住反例见 §4.6；需要引擎做意图缓冲/取消。
   - 特殊技 3/4 顺序 `Z→方向→C/X` 可解析，但 Z tap 会先产生一次软锁（无害，建议引擎在组合完成时抑制或接受）。
   - 现代技能 4（`方向+X+C`）的顺序回退与 3f 方向新鲜窗口**冲突**：2KRO 下建议直接改键，而不是依赖顺序输入。

4. **3f 方向窗口按文档工作**：方向领先 C/X 正好 50ms（3f）仍判方向版；66.7ms（4f）回退基础版；方向已按住 >3f（移动中）回退基础版。60Hz 采样下 50–66.7ms 之间不存在整帧间隔，实际离散到 16.7ms 一档。

5. **发现一处规范张力（需要决策，不是脚本 bug）：按 `docs/00` §4.2 字面优先级「C+X 防御 > Z+X+C 必杀」，Z 按住时若 X→C 间隔 ≤40ms，会把必杀抢判为防御。** 人类三键近同时按时 X/C 间隔通常就在 10–40ms，因此**经典布局的必杀在 NKRO/6KRO 上反而不稳定**。建议改为「Z 按住时 C+X 防御让位/必杀优先」，但这是 `docs/00` 基线变更，需 Human 门批准（见 §6）。
   同时 `docs/03` §4.1 写 C+X ±40ms、§4.3 写 ±50ms，两者冲突，需统一。

6. **软件不能保证的事情**：硬件 ghosting/防冲、键盘固件过滤、OS 粘滞键/筛选键/IME、浏览器快捷键、USB/PS2/蓝牙差异、厂商「6KRO」标称区域差异。软件层只能做启动自检 + 回退提示 + 改键；最终结论必须来自真实键盘人工测试。**本任务未做、也不能做物理键盘测试。**

7. **`manual_test.html` 已交付并做页面逻辑自检**：headless Chrome 中 28 项自检全部通过（DOM、组合判定、顺序输入、报告生成、重置；合成事件只验证页面逻辑，不是硬件证据）。

**决策级判断**：键盘 3f 方向窗口与优先级解析器在模型层可行；NKRO/6KRO 无阻塞。**进入 M0 前需要解决 2 件事**：(a) 经典布局 C+X 防御 vs 必杀的优先级决策；(b) 2KRO 顺序输入的引擎意图缓冲方案（或明确 2KRO 只保证 Space + 改键）。真实硬件风险未闭环，需人工按 §8 跑 2–3 把键盘。

## 1. 范围与方法

### 1.1 范围

按 TASK-062 brief 与 `validation/README.md`：

- 键盘模型：NKRO（不限）、6KRO（≤6 非修饰键）、2KRO（≤2 非修饰键，保守模型）。
- 组合清单：单键（Z/X/C/V/Space/Shift）；`C+X`；`Z+C`；`Z+X`；`Z+X+C`；`方向+C`；`方向+Z+C`；`方向+Z+X`；`方向+Z+X+C`；`方向+X+C`。
- 解析器：3f（50ms）方向窗口、方向已按住 >3f 回退基础版、C+X 防御优先、Z+X+C 必杀优先、Z tap/hold、顺序输入回退（`Z→X→C`、`Z→方向→C/X`）。
- 输出：`combo_matrix.csv`、`manual_test.html`、本报告、`HANDOFF.md`；附加 `context_matrix.csv`（移动/跳跃/斜向上下文）与 `timing_cases.csv`（37 个合成时序用例）。

**非目标**：不做引擎/Unity 实现、不做服务器输入校验、不做手柄、不做物理键盘测试（AI 无法执行）。

### 1.2 键盘计数规则（本报告的统一口径）

| 项目 | 规则 |
|---|---|
| 计数对象 | 非修饰键（non-modifier）：方向键、Z/X/C/V、Space 等；**Shift/Ctrl/Alt 视为修饰键，不计入上限**（假设，见 §7） |
| 方向 | 1 个逻辑方向按 **1 键**计；8 向移动的**斜向 = 2 个方向键**，因此矩阵单列「斜向键数 = 正交键数 + 1」 |

**verdict 标签**：`ok`；`ok_space_optional`（C+X 有 Space 替代）；`ok_cardinal_only`（仅正交方向可）；`sequential_required`（需顺序输入）；`sequential_or_remap`（顺序输入有冲突，建议改键）；`not_a_command`（仅启动自检用，不是战斗指令）。

## 3. 哪些组合需要顺序输入 / Space / 改键（结论清单）

### 3.1 需要「顺序输入」的（2KRO）

| 组合 | 顺序协议 | 软件验证结果 | 备注 |
|---|---|---|---|
| Z+X+C 必杀 | `Z→X→C` ≤250ms，先按后放 | ✅ 可识别（C18）；「干净」有精确前提 | 干净条件：`C↓ − X↓ ≤ 3f(50ms)`（**距 X 按下**，与 X 何时松开无关）且不满足「X 仍按住 且 C−X ≤40ms」（后者判防御）。X 已松开时 C−X ≤50ms 即可；X 仍按住时仅 40<C−X≤50ms 窄带干净；C−X>50ms → 中间动作（Z 按住时特殊 2、Z 已松开时重击）先提交（C19 即此情况）。详见 §4.6 |
| 方向+Z+C 特殊 3 | `Z→方向→C` ≤250ms | ✅ 可解析（C20） | Z tap 会先产生软锁（双动作，建议抑制或接受） |
| 方向+Z+X 特殊 4 | `Z→方向→X` ≤250ms | ✅ 可解析（同类 C20） | 同上 |
| 方向+X+C 现代技能 4 | `方向→X→C` 顺序 | ⚠️ 与 3f 方向窗口冲突 | 若要求方向在 C 前 ≤3f，则「X 按下→X 松开→C 按下」需在 50ms 内完成，几乎不可行；**建议低 rollover 档直接改键** |
| 方向+Z+X+C | 仅启动自检 | — | 不是战斗指令；自检失败 = 键盘滚过上限，应提示顺序输入/改键 |

**顺序输入的引擎前提（TDD 未定义，本验证暴露）**：顺序输入可能跨越 250ms，而 `docs/03` §4.4 只有 2–3 帧输入缓冲。若引擎在 X 按下时立即提交特殊 2/普通重击，必杀就无法再触发。可选方案：
1. 识别 Z 前缀后，把 Z 系列输入（X/C）的提交延迟到 250ms 意图窗口结束，或收到 C 后升级；
2. 状态机允许「特殊 2/重击」被后续必杀取消；
3. 对低 rollover 键盘默认启用「顺序输入模式」并接受 1–2 帧输入延迟；
4. 直接放弃顺序必杀，改为专用键位/宏（例如长按 Z + C 等）。
这些是玩法手感决策，需要 Tech Lead/Orchestrator 定，不能在验证脚本里替选。

### 3.2 需要「Space 替代」的（2KRO）

- **移动中防御**（方向+C+X = 3 键）→ 2KRO 必须用 **Space 防御**：`方向+Space` = 2 键（正交方向）可同按；斜向方向+Space = 3 键仍超限 → 停步。
- 经典布局 Space 防御已验证（C28：Space 按住 + C → GUARD）；现代布局 Space 防御已验证（M07）。
- 建议：启动自检检测到低 rollover 后，**自动建议/切换 Space 防御**，并在设置里保留改键与恢复默认（docs/00 §4.3 已要求）。

### 3.3 需要「改键」的（2KRO）

- 现代技能 4（方向+X+C）：顺序回退与 3f 方向窗口冲突 → 低 rollover 档改键（或接受只能出基础技能 2）。
- 若玩家坚持同时在 2KRO 上使用特殊 3/4 与必杀，顺序输入可用但容错低；改键/专用键位更稳。

## 4. 组合解析器：实现、时序用例与边界

### 4.1 实现规则（`run.py: ComboResolver`）

| 规则 | 实现 |
|---|---|
| 方向窗口 | 方向键**按住**且 keydown 距触发 C/X 的 keydown ≤3f（50ms，闭区间）→ 方向版特殊 3/4 / 现代技能 3/4 |
| 方向已按住 >3f | 回退基础版（特殊 1/2、现代技能 1/2），即「移动中」防误触 |
| C+X 防御 | 经典布局；两键**同时按住**且间隔 ≤40ms；优先级最高（`literal`，文档字面）；现代布局防御 = Space |
| Z+X+C 必杀 | 优先级次高；三键按住，或顺序 `Z→X→C`（keydown 按序、总跨度 ≤250ms、允许先按后放） |
| Z tap / hold | tap ≤150ms（闭区间）→ 软锁；>150ms 视为修饰键；Z 已被组合消费时松开不再软锁 |
| 顺序输入 | 特殊 3/4：`Z→方向→C/X`，方向 keydown 距 C/X ≤3f 且 Z→触发 ≤250ms；必杀：`Z→X→C` ≤250ms |
| 输入缓冲 | 攻击类动作延迟 3f（50ms）提交，更高优先级组合在缓冲内可取消低优先级待提交动作（建模 `docs/03` §4.4 的 2–3 帧输入缓冲） |
| 现代布局 | Z=轻击、C=技能 1、X=重击、X+C=技能 2、方向+C=技能 3、方向+X+C=技能 4、Space=防御、Z+X+C=必杀 |
| 政策开关 | `guard_policy=literal`（默认，防御优先）/ `z_suppresses_guard`（候选修正：Z 按住时防御让位） |

### 4.2 合成时序用例结果（`timing_cases.csv`）

**37 例：PASS=27，EDGE=10，FAIL=0。**

- `PASS`：行为与文档规则直接一致；
- `EDGE`：行为与预期一致，但依赖模型假设（3f 缓冲）或暴露规范张力 → 需要设计与引擎确认；
- `FAIL`：解析器与文档规则不一致（本版 0 例）。

EDGE 清单与含义：

| 用例 | 场景 | 结果 | 含义 |
|---|---|---|---|
| C09 | C+X 间隔 41.7ms（超 ±40ms） | 轻击+重击（非防御） | 40ms 边界外；若采用 §4.3 的 ±50ms 则应为防御（C25 验证） |
| C15 | Z+X+C，X→C 间隔 60ms | 特殊 2 → 必杀 | 中间动作先提交；引擎需取消/缓冲才能干净必杀 |
| C16 | Z+X+C，X→C 间隔 20ms（literal 策略） | **防御**（非必杀） | 规范张力：防御优先级抢判必杀 |
| C17 | Z+X+C，X→C 间隔 50ms（缓冲边界） | 必杀 | 干净必杀仅存在于 (40ms, 50ms] 极窄带（依赖缓冲） |
| C18 | 顺序必杀 Z→X→C（X↓50/X↑60/C↓90，总 90ms） | 软锁→必杀 | 干净：X 已松开且 C−X=40ms ≤3f 缓冲（**距 X 按下**） |
| C19 | 顺序必杀 C 迟到（X↓50/X↑60/C↓180） | 软锁→重击→必杀 | dirty：C−X=130ms >3f 缓冲，X 的待提交重击先提交；引擎必须处理取消/抑制 |
| C20 | 顺序特殊 3 Z→方向→C（总 80ms） | 软锁→特殊 3 | 2KRO 特殊 3/4 顺序回退可行；软锁双动作 |
| C24 | C16 场景 + `z_suppresses_guard` 策略 | **必杀** | 建议修正后可干净触发必杀（需 docs 决策） |
| C25 | C09 场景 + ±50ms 窗口 | 防御 | 证明 §4.1/§4.3 窗口冲突会改变判定 |
| M08 | 现代 C 先 X 后 | 技能 1→重击 | 现代 X+C 顺序敏感，实现需明确顺序 |

### 4.3 3f 方向窗口表现（边界）

| 用例 | 方向领先量 | 结果 | 结论 |
|---|---|---|---|
| C10 | 40ms | 特殊 3 | 新鲜方向生效 |
| C13 | 正好 50ms（3f） | 特殊 3 | **闭区间成立**：≤3f 判方向版 |
| C14 | 66.7ms（4f） | 特殊 1 | 回退基础版；60Hz 采样下一帧 16.67ms，故 50–66.7ms 无整帧档位 |
| C12 | 100ms（已按住移动） | 特殊 1 | 移动中回退基础版，符合防误触意图 |
| M02/M03 | 30ms / 100ms | 技能 3 / 技能 1 | 现代布局同样规则成立 |

**结论**：3f 方向窗口在模型层可行，边界行为确定；真正的风险在「顺序输入回退」与「方向新鲜」的时间竞争（§3.1）。

### 4.4 C+X 防御 vs Z+X+C 必杀的规范张力（重要）

文档原文（`docs/00` §4.2）：`优先级：C+X 防御 > Z+X+C 必杀 > 新鲜方向组合 > 基础特殊 > 普通攻击`。
`docs/03` §4.1 组合优先级表同样把 C+X 防御放在 Z+X+C 必杀之前。

本验证发现：

- 若严格按字面优先级（C16）：Z 按住、X 与 C 间隔 ≤40ms（人类三键近同时按的典型间隔）→ 判定为**防御**，必杀不触发。
- 要让必杀干净触发且无中间动作（C17），X→C 间隔必须落在 **(40ms, 50ms]**（受 3f 缓冲限制）——这是**极窄且不自然**的输入窗口。
- 若采用 ±50ms 窗口（`docs/03` §4.3 的写法），干净必杀窗口退化为空集，问题更严重。
- 候选修正（C24）：**Z 按住时防御让位**（或「Z+X+C 必杀优先于 C+X 防御」），此时 X→C 间隔 20ms 也能干净触发必杀。
- 现代布局不存在该冲突（防御是 Space）：M09 近同时 Z+X+C 稳定解析为必杀。

**建议**：这是经典布局（默认布局）的核心操作手感问题，需 Tech Lead + Human 决策；若要改 `docs/00` §4.2 的优先级，属于基线变更，需 ADR + Human 批准。验证脚本已把两种策略都实现并可复现（`guard_policy` 参数 + C16/C24 用例）。

### 4.6 顺序输入回退的引擎要求（验证暴露的 TDD 缺口）

**先澄清一个易错表述（TASK-063 M3）**：顺序必杀的「干净」条件**不是**「X 松开后 3f（50ms）内按 C」，而是「**C 按下距 X 按下** ≤3f（50ms，输入缓冲）」且**不触发防御抢判**。用 `ComboResolver`（literal 策略、buffer=50ms、guard_window=40ms）按同一脚本逻辑逐点探测如下（本次修正未新增 `timing_cases.csv` 行，按 Lead 指示只改本报告）：

| 输入（ms） | C−X | 输出动作序列 | 说明 |
|---|---|---|---|
| Z↓0, Z↑30, X↓50, X↑60, C↓90（C18） | 40 | `SOFT_LOCK>ULTIMATE` | 干净：X 已松开、C 在 X **按下**后 3f 内 |
| Z↓0, X↓50 按住, C↓70 | 20 | `GUARD` | **X 仍按住反例**：C−X ≤40ms → 防御优先，必杀不触发 |
| Z↓0, X↓50 按住, C↓90 | 40 | `GUARD` | 防御窗口闭区间边界，同样被抢判 |
| Z↓0, X↓50 按住, C↓95 | 45 | `ULTIMATE` | X 仍按住的干净窄带：40 < C−X ≤ 50（防御窗口外、缓冲内；窗口若取 ±50ms 则变 GUARD） |
| Z↓0, X↓50 按住, C↓100 | 50 | `ULTIMATE` | 缓冲边界（闭区间）仍干净 |
| Z↓0, X↓50 按住, C↓101 | 51 | `SPECIAL_2>ULTIMATE` | 超过 3f 缓冲：Z 仍按住时 X 已先提交特殊 2（dirty） |
| Z↓0, Z↑30, X↓50, X↑60, C↓110 | 60 | `SOFT_LOCK>HEAVY_ATTACK>ULTIMATE` | **「松开后 3f」反例**：C 距 X 松开正好 50ms，但 C−X=60ms > 缓冲 → 重击先提交 |
| Z↓0, Z↑30, X↓50, X↑60, C↓180（C19） | 130 | `SOFT_LOCK>HEAVY_ATTACK>ULTIMATE` | 同上，C 迟到更多（dirty） |
| Z↓0, Z↑30, X↓50, X↑60, C↓280（C−Z=280） | — | `SOFT_LOCK>HEAVY_ATTACK>LIGHT_ATTACK` | 超过 250ms：顺序必杀不识别，退回普通轻击 |

**精确条件（经典布局、literal 防御优先、3f 输入缓冲）**：

1. **识别**：`Z↓→X↓→C↓` 按序且 `C↓ − Z↓ ≤ 250ms`（允许先按后放）。
2. **干净（无中间动作先提交）**还需同时满足：
   - `C↓ − X↓ ≤ 50ms`（3f，闭区间；**与 X 何时松开无关**）；
   - 不触发防御：若 C 按下时 X 仍按住，则需 `C↓ − X↓ > 40ms`（±40ms 窗口，闭区间；窗口取 ±50ms 时该窄带消失）。X 已松开则无防御冲突。
3. 因此：**X 仍按住时**，只有 `40ms < C−X ≤ 50ms` 窄带能干净必杀；`C−X ≤ 40ms` → GUARD；`C−X > 50ms` → 中间动作先提交（Z 按住时特殊 2、Z 已松开时重击）。**X 已松开时**，只要 `C−X ≤ 50ms` 即干净（与「松开后多久」无关）。
4. dirty 时解析器仍会在动作列表末尾给出 `ULTIMATE`，因为顺序识别不看中间动作；**不能**把「动作列表里有 ULTIMATE」当作引擎可用——真实引擎若已被中间动作占住状态，必杀通常无法触发。这正是需要引擎意图缓冲/取消的原因。

当前 `docs/03` §4.4 只规定 2–3 帧输入缓冲（33–50ms），不足以覆盖 250ms 顺序输入；若引擎在 X 按下时立即进入特殊 2/重击，必杀将无法触发。
→ 建议在 TDD 输入系统补充「低 rollover 顺序输入模式」的缓冲/取消语义（见 §6 建议 3）。

### 4.7 固定种子模糊回放

- 500 条随机按键序列（seed=20261017，4–9 次按键/序列，含方向/Space），经典布局：
  `deterministic_fail=0`（同一序列两次回放动作完全一致）、`unknown_action=0`、`non_monotonic=0`；动作计数 soft_lock=396、guard=397、ultimate=1。

## 5. 软件不能保证的部分（硬件 ghosting 等）

| 不可保证因素 | 说明 |
|---|---|
| 硬件 ghosting / 防冲 | 键盘矩阵的 ghosting/blocking 由 PCB 走线、二极管、固件决定；同样标称 2KRO 的两把键盘，可用的 3 键组合可能不同。计数模型只能给保守结论 |
| 「6KRO」标称差异 | 部分键盘只保证部分键区任意 6 键，跨区组合可能丢键；本模型按「任意 ≤6」假设 |
| 键盘固件/驱动 | 厂商可能在固件层过滤特定组合、做键位交换、宏/防冲策略 |
| OS 层过滤 | Windows 粘滞键/筛选键/切换键、IME、远程桌面、虚拟机、云电脑会吞键或改写按键 |
| 浏览器/窗口层 | 浏览器快捷键、焦点丢失、游戏内全屏/输入法状态可能改变按键上报 |
| 连接方式 | USB 轮询率、PS/2、蓝牙、无线 2.4G 的丢包与延迟差异未建模 |
| 输入时序 | 本验证用理想时间戳；真实 OS 输入延迟、抖动、60Hz 采样量化未建模 |
| 物理手感 | 3 键同按的可行性还受键帽/手指/玩家操作习惯影响 |

**软件层能做**：启动自检（docs/03 §4.3 的组合）、检测同时按键数、提示顺序输入/改键、提供 Space 防御替代、保存低 rollover 档位配置、训练场可视化。
**软件层不能做**：保证任意硬件都能同时上报 3/4 键，或区分「硬件丢了键」和「OS 吞了键」。

**人工验证协议（`manual_test.html`）**：至少 3 把键盘（NKRO、标称 6KRO、办公薄膜/笔记本），关闭粘滞键/IME，用**物理按键**逐项测试；页面记录「观测最大同时键数」与顺序输入总时长，导出报告。**本任务没有执行该人类测试，结果待填。**

## 7. 限制与待核实

- **模型级，不是引擎实测**：解析器是无状态机模型（3f 缓冲 + 优先级分类），未模拟动画状态、取消窗口、网络输入、服务器校验。真实引擎行为可能不同。
- **不是物理键盘测试**：本报告没有任何真实键盘数据；`manual_test.html` 只提供人工测试工具，AI 未执行（任务书要求的 2–3 把键盘测试待人工完成）。
- **矩阵 ghosting 未建模**：2KRO 结论是计数意义上的保守结论；真实键位 ghosting/防冲未模拟（§5）。
- **6KRO 假设**：按「任意 ≤6 非修饰键」假设；厂商区域差异未建模。
- **修饰键假设**：Shift/Ctrl/Alt 不计入上限；部分低价键盘修饰键与主键区共享线路，可能实际占用 rollover（未建模，标记待核实）。
- **时序理想化**：时间戳为理想值；未含 OS 输入延迟/抖动、USB 轮询、蓝牙延迟；60Hz 采样量化已说明。
- **3f/窗口语义**：按 `docs/00` §4.2 的「≤3f」实现为闭区间；C+X 窗口的 40/50ms 冲突按 §4.1 的 40ms 建模并单独测试 50ms 变体（C25）。
- **「同时按住」语义**：C+X 防御要求两键都按住（避免顺序输入误判）；Z+X+C 必杀支持顺序输入（文档明确）；其余组合的「同时/顺序」语义未在 docs 中逐条定义，按本文假设实现。
- **待核实**：真实薄膜键盘 2KRO/3 键行为；「6KRO」厂商标称；OS/浏览器吞键情况；玩家 3 键同按的实际时间分布（建议 instrumentation/playtest 采集）。
